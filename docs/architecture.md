# Architecture Decisions

This workflow-facing document summarizes the authoritative designs in `Architecture.md`, `Techstack.md`, and `database.md`.

## System shape

The product is a React TypeScript SPA served by Caddy and a single Go service. The service accepts device telemetry over HTTPS, authenticates/validates/rate-limits it, enqueues accepted work in bounded in-memory device shards, computes aggregates, publishes derived state to Redis, and persists raw events to PostgreSQL in batches.

The synchronous admission path performs no Redis or PostgreSQL work. A `202` therefore means in-memory admission only, not durable storage.

## Modules and boundaries

| Module | Owns | Confirmed seam |
|---|---|---|
| Ingestion | Device credentials, batch validation, per-device rate limiting, admission decision. | Admit a telemetry batch and return accepted count or documented typed rejection. |
| Telemetry | Device-sharded processing, five-minute aggregates, thresholds, Redis publication, PostgreSQL batch persistence, retry/backpressure. | Process an accepted batch and expose processing/dependency state. |
| Fleet | Redis-backed fleet/device live snapshots and their UI destinations. | Read a fleet or device live snapshot, including freshness and degraded mode. |
| History | Bounded manual raw-event query and its UI destination. | Query a device’s manually requested bounded history result. |

Modules represent product concepts, not technical layers. A Go module exposes its package API; a frontend module exposes only its `index.ts` public interface. Cross-module access uses only those declared interfaces. HTTP/OpenAPI is the seam between frontend and backend.

## Data and lifecycle

- PostgreSQL is the durable raw-event system of record; Redis is rebuildable derived state.
- Telemetry events are immutable. They are not edited or deleted in MVP.
- Devices and API credentials are seeded/controlled outside the dashboard; neither has an MVP lifecycle screen.
- Manual history is bounded and user initiated. Live pages never fall back to PostgreSQL reads.
- Redis failure permits persist-only processing when PostgreSQL is healthy. PostgreSQL failure eventually activates bounded admission backpressure.

## Stack

- Frontend: React, TypeScript, Vite, TanStack Query, Recharts, Tailwind/shadcn accessibility primitives, Lucide.
- Backend: Go, `net/http`, `chi`, `pgx`, `go-redis`, `slog`, Prometheus client.
- Storage: PostgreSQL and Redis.
- Deployment: Docker Compose on Ubuntu, Caddy, Prometheus, Grafana, and systemd.

## Non-functional decisions

- Target benchmark: 2,000 requests/sec at 10 events/request, generated by at least 2,000 device credentials.
- Admission p95 target: under 20 ms. Redis-backed read p95 target: under 5 ms.
- Static device API keys use a key ID plus high-entropy secret, HMAC hash comparison, and TLS only.
- Queue/retry memory is bounded. The system makes loss boundaries visible rather than claiming unsupported durability.
- All application success and error responses use JSON and include `X-Request-ID`. `GET /metrics` is the deliberate exception: it returns Prometheus text exposition as `text/plain; version=0.0.4`, still with `X-Request-ID`, so Prometheus can scrape it correctly.
